## 0. 结论速览

| 站点 | 目标数据可否不解图读取 | 最大障碍 | 建议优先级 |

## ★ 1. 本轮最重要的发现：`Turrets` 其实可以被抽象，而它是囚犯线 100% 的守卫

### 1.1 事实

`SitePartWorker_Turrets.GenerateDefaultParams` `[验证]`（在**任务生成时**就被调用，结果存进 `SitePartParams` 并随存档持久化）：

```csharp
sitePartParams.mortarsCount = Rand.RangeInclusive(0, 1);
sitePartParams.turretsCount = Mathf.Clamp(
    Mathf.RoundToInt(sitePartParams.threatPoints / ThingDefOf.Turret_MiniTurret.building.combatPower),
    2, 11);
```

| 项 | 值 `[验证]` |
|---|---|
| `Turret_MiniTurret.building.combatPower` | **45** |
| `turretsCount` | `Clamp(round(威胁点数 / 45), 2, 11)` ⇒ **2–11 座迷你炮塔** |
| `mortarsCount` | `Rand.RangeInclusive(0, 1)` ⇒ 0–1 座迫击炮 |
| 炮塔枪 `Gun_MiniTurret` | 射程 **28.9** 格、burst **2** 发、发间隔 8 ticks、弹 `Bullet_MiniTurret` |
| `Gun_MiniTurret.statBases` 四段精度 | Touch **0.77** / Short **0.70** / Medium **0.45** / Long **0.24** |
| `RangedWeapon_Cooldown` | **4.8**（= 288 ticks ⇒ 每 250-tick 回合约 **1.74** 次连发） |
| `Bullet_MiniTurret` | `damageAmountBase` **12**、`armorPenetrationBase` **-1**（哨兵值 ⇒ 破甲要另取，见下） |

⇒ **炮塔的编制是完全确定性的、写在存档里的整数**，和 `SleepingMechanoids` 的种子、`Outpost` 的 `GetPawnGroupMakerSeed` 属于同一类"可复现"数据。
DESIGN §18.3 把 `Turrets` 判为 `ForbidAbstract`（"固定火力无法抽象"）**与数据不符** —— 无法抽象的是"**布局**与**触发时机**"，而这两件事在无地图模型里本来就被
`CombatScene.EnemyOutputFactor`（§18.3 的 `abstractPenalty`）与 `HasTerrainAdvantage` 吸收掉了。

### 1.2 为什么这条最值钱

`Turrets` 出现在四条线里 `[验证]`（按 SitePartDef.tags 反查）：

| 标签 | 池成员 | 谁在用 | 炮塔占比 |
|---|---|---|---|
| `PrisonerRescueQuestThreat` | **仅 `Turrets`** | 囚犯营救 | **100%** |
| `ItemStashQuestThreat` | AmbushEdge, AmbushHidden, Manhunters, MechCluster, SleepingMechanoids, Turrets, Outpost | 物品藏匿点 | 1/7 |
| `DownedRefugeeQuestThreat` | 同上 7 个 | 难民营救 | 1/7 |
| `MineralScannerPreciousLumpThreat` | AmbushEdge, AmbushHidden, Manhunters, MechCluster, SleepingMechanoids, Turrets, Outpost | 远程矿物扫描仪矿点 | 1/7 |

⇒ **只做 `Turrets` 一件事，就把囚犯线从"0% 可评估"变成"100% 可评估"**，顺带把物资/难员/矿点各救回 1/7。

### 1.3 建模提案 `[建议]`

炮塔是 `CombatUnitSnapshot` 里最容易表达的一类，因为现有模型已经够用：

```csharp
new CombatUnitSnapshot {
    Name           = "迷你炮塔 ×" + parms.turretsCount,
    IsMine         = false,
    MaxHealth      = Turret_MiniTurret 的等价耐久 × count,   // 或按 count 拆成多个单位
    Range          = 28.9f,
    MoveSpeed      = 0f,          // ★ 固定火力：不推进、不后撤
    IsMelee        = false,
    HasTerrainAdvantage = true,   // ★ 工事
    AccuracyNear   = 0.77f,       // Gun_MiniTurret AccuracyTouch
    AccuracyFar    = 0.24f,       // Gun_MiniTurret AccuracyLong
    ShotsPerRound  = 250f / 288f * 2f ≈ 1.74f,
    DamagePerShot  = 12f,         // Bullet_MiniTurret damageAmountBase
    ArmorPen       = 待取（见下）,
    ArmorRating    = 待取（见下）,
}
```

**需要注意 / 可能要改的地方 `[UNVERIFIED]`：**

1. **`MoveSpeed = 0` 的副作用**：`CombatScene.SideAdvanceSpeed(mine: false, ...)` 取的是"尚未进入射程的己方单位里最慢的那个" ⇒ 敌方推进速度变 0。
   这正是我们要的（炮塔不冲锋），但要确认核心不会因为 `slowest == 0` 而卡死或除零。
2. **破甲 `armorPenetrationBase = -1` 是哨兵值** `[验证]`：原版取 `-1` 表示"回退到别的来源"，
   需要另取 `Gun_MiniTurret` 的 `ArmorPenetrationSharp` 或 `verbProperties.armorPenetration`，
   **不能**直接把 -1 塞进 `CombatUnitSnapshot.ArmorPen`（那会让炮塔完全打不穿护甲）。
3. **炮塔建筑的耐久与护甲**：`Turret_MiniTurret` 的 `statBases.MaxHitPoints` / `ArmorRating_*` 用 CLI 的字段路径没取到
   （可能不在 `statBases` 里），需要再查一次；它决定"冲进去要挨几轮"。
4. **`EquilibriumDistance()` 不看阵营**，取的是全场最小有效射程 ⇒ 交火距离由"我方最短射程"决定，炮塔（28.9）通常够得着。
   于是战斗形态自然变成"**顶着炮塔往上冲**"，符合原版体验。
5. **迫击炮（0–1 座）**：`Turret_Mortar` 的 `verbs[0]` 读不出射程/弹药（它是迫击炮专用组件），建模成本明显高于迷你炮塔。
   建议 v1 **先只做迷你炮塔**，迫击炮用 `EnemyOutputFactor` 的少量加成近似，并在预告面板的"评估假设"里写明 `[建议]`。
6. 炮塔的**耐久**：`Building_TurretGun` 是高耐久建筑，把它摊成"1 个高血单位"还是"N 个 45 战力的小单位"，会明显影响战斗长度与伤亡分布 —— 建议做成 Def 可调，先各跑一次看手感。

### 1.4 顺带能一起做的 `AmbushEdge` / `AmbushHidden`？`[建议]` 先别

`SitePartWorker_Ambush.GenerateDefaultParams` `[验证]` 只做了一件事：

```csharp
sitePartParams.threatPoints *= 0.8f;
```

它**不写任何种子或编制**（伏击的 pawn 是由 `GenStep_Ambush`-类生成器在地图生成时现掷的）。
所以伏击也能"按点数生成一队人"，但：
- 没有可复现的种子 ⇒ 预告与真进图**不可能逐人一致**（而 `Outpost` / `SleepingMechanoids` / 现在的 `Turrets` 都能）；
- 伏击的**触发时机与先手**才是它的杀伤力来源，那正是无地图模型最难表达的东西（`HasTerrainAdvantage` 只能给个笼统折扣）。

⇒ 建议：`AmbushEdge` / `AmbushHidden` / `MechCluster` 维持 `ForbidAbstract`，但在 UI 里把原因说清楚
（现在的文案是"无法无地图评估（需进图）"，够用）。要做的话应当配一个明确的首手折扣参数，而不是硬塞。

## 2. `PreciousLump`（矿点）—— 已实装，还剩三个真问题

### 2.1 现状（不再复述 DESIGN §1，只列与本轮相关的）

`[验证]` `part.parms.preciousLumpResources` 存矿种；`GenStep_PreciousLump` 用价值区间 3500–5000 现掷格数；
30 天超时、`inSignalDisable = site.MapGenerated`；`forceExitAndRemoveMapCountdownDurationDays = 11`；50% 概率带 1 个威胁件。

### 2.2 问题一：存量与"真进图"是两次独立掷骰（DESIGN §7.1 自己承认未堵）

**现状**：委派按公式算出"总格数"，玩家真进图时 `GenStep_PreciousLump` 会**再掷一次**。采空路径靠 `site.Destroy()` 兜住；**没采空就进图**则两边数字对不上。

**候选解法 `[建议]`（按代价从低到高）**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 诚实标注 | 在委派 inspect 面板与完成信件里写明"存量由委派独立推算，与原版进图掷骰**不一定一致**" | 0 代码风险，但把问题甩给玩家 |
| B. 一次委派即锁定 | 委派**开始时**就把 `dep.rolledUnits` 写进同一个 `SitePartParams`（新增一个 mod 字段 / `modExtensions`），GenStep 读它 | 需要 `GenStep_PreciousLump` 的 Harmony patch（读 `parms.sitePart.parms`）—— 这是全 mod 少见的必须 patch 的地方 |
| C. 委派过就禁止进图 | 有 `deposit.HasBeenWorked` 时，`CaravanArrivalAction_VisitSite` 的入口灰掉 | 便宜，但剥夺了玩家"我就要进图打"的自由，容易被骂 |
| D. 反向：委派**先**触发一次 GenStep | 不生成地图，只调 `GenStep_PreciousLump.Generate` 到一张临时/空地图上取数 | 不可行（GenStep 需要真 `Map`） |

⇒ **建议 A + B**：先上 A（零风险、立刻诚实），B 作为 P2 的单独工作项（它同时能解决"委派中途进图"的所有不一致）。

### 2.3 问题二：小行星采矿点**不是 `Site`**，委派入口根本不存在

这是 DESIGN §9 的 P2 `RimDelegation_MineAsteroid` 的**结构性障碍** `[验证]`：

| 项 | `PreciousLump` 路线 | Odyssey 小行星 |
|---|---|---|
| 世界对象 | `WorldObjectDef "Site"`（`worldObjectClass = RimWorld.Planet.Site`） | `WorldObjectDef "AsteroidMiningSite"`（`worldObjectClass = **ResourceAsteroidMapParent**`） |
| 继承链 | `Site : MapParent : WorldObject` | `ResourceAsteroidMapParent : SpaceMapParent : MapParent : WorldObject` —— **完全不含 Site** |
| `def.comps` | 9 个（委派 comp 由 XML patch 注入） | **空数组**（`[]`） |
| 部件数据 | `SitePartParams.preciousLumpResources` | 无部件；矿种来自 `OpportunitySite_Asteroid` 的 `QuestNode_Root_Asteroid { mineables: [Gold, Plasteel, Uranium] }` |
| `SitePartWorker_Asteroid` | 只在 `Init` 里用 `preciousLumpResources` 拼个 label；**当前加载顺序里没有任何 `SitePartDef` 用它** | — |

⇒ 想覆盖小行星，需要三件事一起做：

1. 把委派 comp 也 patch 到 `AsteroidMiningSite`（它 `comps` 为空，patch 得用 `PatchOperationAdd` 建 `<comps>` 节点，注意 xpath 要能建不存在的节点）；
2. `WorldObjectComp_Delegations.Site => parent as Site` 这一行到处在用（gizmo/float menu/检视/存读档）—— 要么泛化成 `MapParent`，要么为小行星单独开一条只读分支；
3. 矿种与规模得从 `QuestNode_Root_Asteroid` / `Asteroid` mapGenerator 那条路取，**不能**复用 `SitePartParams`。

⇒ **建议**：先明确"委派框架的宿主是 `Site`"这个边界（写进 DESIGN），把小行星从 P2 降级到 P3；或者**只做 P2 的第二半**：让 `RimDelegation_MinePreciousLump` 的 worker 支持 `SitePartWorker_Asteroid` 部件（如果将来有 mod 用 `Site` + 小行星部件）。

### 2.4 问题三：委派一暂停超时，就没有任何时间压力了

**现状**：`handleTargetTimeout = Pause` 把 30 天冻住。采矿本身要 2–25 天（技能决定），所以委派期间玩家只是在等，**没有风险曲线** —— 随机事件是唯一的变量。

**头脑风暴 `[建议]`**：

- **E1. 被抢占（最贴合原版叙事）**：原版超时的信件就是"那批物资已经被人捷足先登"。委派期间按天 roll「别人也发现了这个矿点」，
  命中则矿点规模缩减（偷走一部分 `deposit.totalUnits`）或直接失败。**可以直接复用 `DelegationEventDef` 框架**（新增一个 `DelegationEventDef_RivalClaim`），零新基建。
- **E2. 矿脉枯竭/涌水（已有 CaveIn 的兄弟）**：`CaveIn` 已经是"埋掉已采部分"，可以加"涌水淹没矿格"（扣总规模）。
- **E3. 疲劳 → 工伤（已实装）** 已经是长工时的代价；可以再加"连续夜班 → 采矿技能临时下降"。
- **E4. 侦察暴露**：委派停留越久，被该派系发现并派袭击的概率越高（`Caravan` 的 `IncidentTargetTags` 本来就吃袭击事件）。
  这条**几乎免费**：只要不暂停超时、或者给委派加一个"暴露度"。

> 我倾向 **E1 + E4**：两者都不需要新系统，且把"30 天"从装饰变成真正的决策（"派几个人、用哪个模式"开始有对错了）。

## 3. `DownedRefugee`（难员）

### 3.1 引擎事实（全部 `[验证]`）

| # | 事实 | 位置 |
|---|---|---|
| 1 | 难员是 `SitePart.things[0]` 里的一个 `Pawn`，**任务生成时就存在**，`Scribe_Deep` 持久化 ⇒ **不解图可读、可存读档** | `SitePartWorker_DownedRefugee.Notify_GeneratedByQuestGen` + `SitePart.ExposeData` |
| 2 | 生成方式：`PawnKindDefOf.SpaceRefugee` → `DamageUntilDowned(allowBleedingWounds: false)` → **`DamageLegsUntilIncapableOfMoving(allowBleedingWounds: false)`** | `DownedRefugeeQuestUtility.GenerateRefugee` |
| 3 | ⇒ **倒地 + 双腿不能走 + 不流血**（不会自己死） | 同上 |
| 4 | `SitePart.SitePartTickInterval` 会把 `things` 里的 Pawn 食物顶在 **0.8** ⇒ **不会饿死** | `SitePart.SitePartTickInterval` |
| 5 | 超时 **7–15 天**（`randInt(7,15)*60000`），`inSignalDisable = site.MapGenerated`，到期「失去联络」+ `End Fail` | `OpportunitySite_DownedRefugee` |
| 6 | 威胁池与物资点**完全相同**的 7 个，`siteThreatChance = 0.7`，`hiddenSitePartsPossible = true` | 同上 |
| 7 | **`GenStep_DownedRefugee.ScatterAt` 的取值优先级**：`part.things` → `DownedRefugeeComp.pawn` → 现生成；并设 **`pawn.mindState.WillJoinColonyIfRescued = true`** | `GenStep_DownedRefugee` |
| 8 | `WillJoinColonyIfRescued` 是"**救下即必定加入**"的开关；普通被救者走 `AITuning.RescuedPawnJoinChance_OutsideDangerous/OutsideSafe` 的**概率**加入 | `Pawn_GuestTracker.RandomizeJoinStatus` / `AITuning` |
| 9 | 原版**允许把倒地 pawn 编入远行队** | `CaravanFormingUtility.IsFormingCaravanOrDownedPawnToBeTakenByCaravan(pawn)` |
| 10 | 站点被销毁时**不杀**难员：`Notify_FailedRescueQuest()`（关系记恨）+ 治疗非永久伤 + 恢复双腿，然后 `PassToWorld` | `SitePartWorker_DownedRefugee.PostDestroy` → `SitePart.PostDestroy` |
| 11 | 任务注册的"奖励"是**空壳**：`QuestNode_AddPawnReward` 只把 `Reward_Pawn` 塞进 `QuestPart_Choice`，**从不调** `GenerateQuestParts`；而 `Reward_Pawn` **没有覆写** `Notify_Used`（基类只置 `usedOrCleanedUp = true`） | `QuestNode_AddPawnReward.RunInt` + `Reward.Notify_Used` |

**第 11 条极其重要**：`inSignalChoiceUsed = "site.MapGenerated"` 看起来像"进图就给你人"，其实**什么都不做**。
⇒ **不要指望发一个信号就能让难员加入**，委派必须自己完成"加入"这件事。

### 3.2 设计概念

**概念 A · 远程营救（纯委派，不进图）`[建议]`**

```
车队抵达 → （若有守军）威胁评估 → 战斗结算（复用 CombatScene）
  胜 → part.things.Take(pawn)
      → pawn.mindState.WillJoinColonyIfRescued = true     // 对齐原版意图
      → caravan.AddPawnOrItem(pawn, false)                // 原版允许抬倒地者
      → 撤走；回殖民地后 pawn.SetFaction(Faction.OfPlayer) // 或走 guest 流程
```

- 复用度最高：`DelegationWorker` 的骨架与 `DelegationWorker_TakeItemStash` **几乎一样**（目标容器从"物资清单"变成"一个人"）。
- **`totalCells` 用不上**（就 1 个人）⇒ 进度单位改成"**稳定度/救治进度**"更自然：委派不是"搬 1 件"，而是"花 N 天把人治好到能抬走"。
- 关键风险 `[UNVERIFIED]`：`Pawn` 进 `Caravan` 后，车队移动、负重、原版 UI 是否都正常（`CaravanFormingUtility` 只证明"编队时允许"，不证明"世界地图上行进时正常"）；倒地者是否会拖慢车队需要实测。

**概念 B · 两段式：委派清场，进图接人 `[建议]`**

- 委派只做"压制/清除守军"（复用 `CombatScene` 的 Resolving），把守军打掉；
- 难员**必须**玩家进图接（因为"救下即加入"的原版消费点在地图侧的 `JobDriver_TakeToBed` / `Pawn_GuestTracker`）。
- 优点：完全不动原版加入流程，风险最低；缺点：与 mod 的"不进图"卖点相悖，只能算过渡。

**概念 C · 把 7–15 天变成真压力 `[建议]`**

原版既不流血也不饿死 ⇒ 等待是**零成本**的，这浪费了整个时限设计。
建议委派期间给难员挂 mod 自己的恶化机制（复用 `DelegationEventDef`）：

| 事件 | 效果 |
|---|---|
| 伤势恶化 | `Hediff` 严重度 +，到阈值 → 委派失败、任务 Fail |
| 感染 | 挂 `HediffDefOf.WoundInfection`（对齐原版 `allowBleedingWounds: false` 但感染仍可能） |
| 天气/野兽 | 打断"远程稳定"进度 |

⇒ 于是"派谁去、带什么药、走哪条路"开始有对错。

**概念 D · 治疗投入 `[建议]`**

`DelegationDef.skillDef = Medicine`，速率按**医生技能 × 药品质量**算（可以照抄 `DelegationWorker_TakeItemStash` 的"预算"结构：
每 tick 生成"救治预算"，花在"稳定度"上）。消耗车队里的 `Medicine*`。
这条把"物资点搜刮"与"难员营救"串成一条链：**先去搜刮拿药，再去救人**。

### 3.3 与现有框架的接线点

| 项 | 结论 |
|---|---|
| 目标定位 | 与 `LootOwner` 同构：遍历 `site.parts`，找 `def.targetSitePartTags` 命中的 part，读 `part.things[0] as Pawn` |
| 超时暂停 | `handleTargetTimeout = Pause` 直接可用（同一个 `QuestPart_WorldObjectTimeout`） |
| 完成即销毁 | `destroyTargetOnComplete` ⇒ `site.Destroy()` ⇒ 触发 `QuestNode_NoWorldObject` 结束任务 ✓ 天然闭环 |
| 失败路径 | 若委派中止且不销毁站点，难员留原地、计时恢复，可再来 ✓（与物资点同一套） |

### 4.2 设计概念

**概念 A · 先支持 `Turrets`，再谈囚犯 `[建议]`（P0）**

因为守卫 100% 是炮塔，**"囚犯线能不能做"完全等价于"炮塔能不能抽象"**。按 §1.3 实现炮塔单位之后：

- 囚犯营救 = "顶着 2–11 座迷你炮塔冲进 8×8 牢房把人抬走"；
- 这条**恰好是无地图模型的强项**（固定火力 + 固定距离 = 教科书式的可算）；
- 而它在原版里是最难的地图战之一（炮塔密集 + 牢房狭窄），⇒ **委派提供的价值最大**。

**概念 B · "潜入"而非"强攻" `[建议]`**

`prisonCell` 在进图时是**未探明**的（第 7 条）⇒ 叙事上这本来就是一次**潜入**。
可以给 `RimDelegation_RescuePrisoner` 一个与强攻并列的模式轴：

| 模式 | 机制 | 代价 |
|---|---|---|
| 强攻 | 跑 `CombatScene`（炮塔 vs 车队），赢了抬人 | 伤亡；炮塔火力下大概率重伤 |
| 潜入 | 按 `潜行技能（潜行/射击/格斗取高）+ 人数` 算暴露概率；成功则**不触发炮塔**，直接开门带人 | 失败 = 被炮塔打一轮（`EnemyOutputFactor` 拉高） |

⇒ 这是一条**真正新的玩法轴**，而且实现上只是在 `CombatScene` 外面包一层"要么交战、要么掷暴露"的分支。

**概念 C · 他是"囚犯"，加入流程要小心 `[UNVERIFIED]`**

囚犯带着 `GuestStatus.Prisoner` + `hostFaction`。直接 `SetFaction(Faction.OfPlayer)` 可能绕过 `Pawn_GuestTracker` 的招募/心情/关系流程，
造成"加入但没有加入记忆、关系也没更新"。候选做法（需实测择优）：

1. `pawn.guest.SetGuestStatus(null)` 清掉囚犯身份 → `pawn.SetFaction(Faction.OfPlayer)`（最直接）；
2. 走原版招募：`RecruitUtility.Recruit(pawn, Faction.OfPlayer)`（如果有这个入口，最"正统"）；
3. 只把人抬进车队、让他以**囚犯**身份到殖民地，由玩家自己招募（最保守，但违背"他会加入"的任务承诺）。

**概念 D · 叙事红利 `[建议]`**

`forceRedressWorldPawnIfFormerColonist: true` 与任务文案里的 `formerColonistInfo` ⇒ **他可能是你以前的殖民者**。
委派可以在任务描述/信件里把这一层放大（"你救回的是三年前走失的那个人"），零机制成本、纯文案收益。
另外 `PawnKindDefOf.Slave` + `ChildrenAllowed` ⇒ 可能是小孩，需要确认 §3 的"抬人"逻辑对 `DevelopmentalStage.Child` 同样成立。

### 4.3 接线点

与难员几乎相同，唯一额外项：**加入流程**（概念 C）。

### 8.1 任务 1 · 炮塔抽象（`Turrets`: ForbidAbstract → Abstractable）

| 文件 | 改动 |
|---|---|
| `Combat/Game/CombatSnapshotFactory.cs` | 新增 `FromTurret(turretDef, gunDef, name, out problem)` + 4 个私有助手 |
| `Combat/Game/ThreatRosterFactory.cs` | `SupportOf` 把 `Turrets` 移入 `Abstractable`；新增 `GenerateTurrets`；`Build` 的内层 switch 加分支 |
| `Combat/Game/Dialog_ThreatAssessment.cs` | 编队列表**同名同数值合并成一行**（"迷你炮塔 ×7"） |

**炮塔快照怎么来的**（全部走 vanilla 自己的函数，不自己发明公式）：

```csharp
Range          = Gun_MiniTurret.verbs[0].range            // 28.9
AccuracyNear   = ShotReport.HitFactorFromShooter(turret, 8)
               × vp.GetHitChanceFactor(gunThing, 8)        // 0.53
AccuracyFar    = 同上 @ 28.9                                // 0.12
ShotsPerRound  = max(turretBurstCooldownTime, RangedWeapon_Cooldown) + warmup  // 4.8s → 1.74
DamagePerShot  = Bullet_MiniTurret.GetDamageAmount(gun)    // 12
ArmorPen       = Bullet_MiniTurret.GetArmorPenetration(gun) // -1 被 vanilla 解析成 12×0.015 = 0.18
MaxHealth      = Turret_MiniTurret.GetStatValue(MaxHitPoints) // 100
MoveSpeed      = 0           // 固定火力
HasTerrainAdvantage = true   // 工事
```

三个关键点：

1. **非 Pawn 射手走的是另一条命中公式**：`ShotReport.HitFactorFromShooter(Thing, distance)` 里
   `caster is Pawn` 才用四段曲线；非 Pawn 是 `ShootingAccuracyTurret(0.96) ^ distance`，下限 0.0201。
   模型在两点之间线性插值 ⇒ 与 pawn 一样是"两点近似"，已写进注释。
2. **武器精度必须传枪的 Thing**：`Gun_MiniTurret` 的 verb 级 `accuracyTouch..Long` 全是 1，
   真值（0.77/0.70/0.45/0.24）在 `statBases` 里，只有 `GetHitChanceFactor(gun, dist)` 才会读到。
3. **`armorPenetrationBase = -1` 是哨兵值**：不要自己填，调 `GetArmorPenetration` 让 vanilla 解析（→ 0.18）。

**一个被改掉的性能缺陷**：`RescueUtility.GuardUnitCount` 原本调 `ThreatRosterFactory.Build` 数敌人，
而它会被委派对话框**每帧**调用（`ApproachForecast` → `StealthExposure`），那等于每帧造 11 座炮塔 + 11 把枪。
改成纯数据读取：炮塔数直接读 `SitePartParams.turretsCount`（本来就精确），其它按
`威胁点数 / 75` 估算 —— 只影响"该躲还是该冲"的手感，不影响任何结算。

**原版"入伙"的实际路径**（这是本轮最重要的反编译结论）：

```csharp
// 看起来像奖励，其实是空壳：
//   QuestNode_AddPawnReward 只把 Reward_Pawn 塞进 QuestPart_Choice，
//   而 Reward_Pawn **没有覆写** Notify_Used（基类只置 usedOrCleanedUp = true）
//   ⇒ inSignalChoiceUsed = "site.MapGenerated" 其实什么都不做。
//
// 真正的路径：
RecruitUtility.Recruit(pawn, Faction.OfPlayer, recruiter);
//   内部 = apparel.UnlockAll → royalty 头衔替换
//          → guest.SetGuestStatus(null) → SetFaction(faction, recruiter)
//          → guest.Notify_PawnRecruited()
//   唯一的 Spawned 分支是地图注册表刷新，未 spawn 时自动跳过 ⇒ 地图无关
QuestUtility.SendQuestTargetSignals(pawn.questTags, "Rescued", pawn.Named("SUBJECT"));
//   与 JobDriver_TakeToBed.CheckMakeTakeeGuest 发的信号一致
```

**倒地 Pawn 能进车队**（反编译确认）：`Caravan.AddPawn` 只拒绝 `null` 与 `Dead`，
**没有 `Downed` 守卫**，而且自带 `ShouldAutoCapture(p)` 分支。
⚠️ 所以顺序必须是 **先 `Recruit` 再上车**，否则刚救出的人会被当俘虏收押。

**清场结算**：`CombatSceneFactory.Build` → `CombatSimulator.Simulate`（种子存进 `d.rolledValue`）
→ `ThreatCleared` 才进入"抬人"阶段，否则 `workerAbortReason` 让宿主**中断**（地点保留、计时恢复）。

**伤亡真的落实**：按 `UnitReport.Name`（= `LabelShortCap`）映射回参与者；
死亡量用**本模型自己的尺子**折算（`(当前耐久比例 - 目标耐久比例) × 100`，与
`CombatTuning.HealthPoolPerScale = 100` 同量纲）。阵亡默认是真的，可用
`DelegationDef.casualtiesArePermanent = false` 降级为倒地。

**"守军先手一轮"落在哪**：折算成我方开局的耐久折扣，作用在 **`CombatScene` 快照**上
（`CombatSceneFactory.ApplyFirstStrikePenalty`）。这样委派结算与对话框里的「威胁评估」
看到的是**同一个战场** —— 维持"预告即契约"。

**进度**：单位 = 百分点（0..100）。`RescueUtility.PercentPerHourPerPawn = 12`
⇒ 单人正常工作（8h/天）约 **1.04 天**。技能系数 `0.6 + 0.04 × 等级`（0 级 0.6 → 20 级 1.4）。

### 8.3 任务 3 · 矿点存量一致性

**诚实标注**：`DelegationWorker.InspectWarning`（新虚方法）→ 宿主把它打在地点检视面板上。

site.GetComponent<EnterCooldownComp>().Start(def.blockMapEntryDays);   // Start(float?)
