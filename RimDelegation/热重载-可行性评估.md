# RimDelegation 热重载可行性评估

> 调查对象：调试 RimDelegation 时能否用"热加载"改代码，以及"dll 被占用、无法修改"的根因。
> 证据来源：RimWorld 1.6 反编译（`Assembly-CSharp.dll`，DecompilerServer 上下文 `rw16`）+ 本机实测文件状态 + `Player.log` 运行痕迹。
> 标记约定沿用 DESIGN.md：`[验证]` = 反编译/实测证据；`[建议]` = 提案；`[UNVERIFIED]` = 未验证。

---

## 0. 结论速览

| 改动类型 | 能否热重载 | 手段 | 备注 |
|---|---|---|---|
| **C#（`RimDelegation.dll`）** | **可以（方法级）** | 第三方注入：Doorstop + ILReloaderLib，靶子方法打 `[Reloadable]` | 2026-09-30 本机实测跑通（§6）；只换方法体，类型身份与字段不变 |
| 已有 Def 的**数值/字段**（`Defs/*.xml`） | 可以 | 调试动作 `General → Hot reload Defs`，或 Hot Reload mod | 机制是"就地改写旧 Def 实例"，引用不失效 |
| **新增 / 改名** Def | 不能（半残） | 同上，但 `[DefOf]` 字段会是 null | 热重载路径不调 `DefOfHelper.RebindAllDefOfs` |
| `[StaticConstructorOnStartup]`（ModBoot 自检、静态缓存） | 不会重跑 | — | `CallAll()` 只在完整启动流程末尾调用 |
| 贴图 / 音频 / 字符串资源 | 可以 | **只有** Hot Reload mod（原版不做） | 原版 hotReload 时 `ReloadContentInt` 直接 return |

**关于"dll 占用"的准确结论** `[验证]`：被锁的**不是**你 `build.ps1` 写的那份，而是**游戏 `Mods\RimDelegation\` 里由 `deploy.ps1` 镜像过去的那份**。构建不受影响，**部署**会被锁挡住。

`[验证]`（2026-09-30 补）这把锁的根因可解：Doorstop 会把 `ModAssemblyHandler.ReloadAll` 里的 `Assembly.LoadFrom` 替换成 `Assembly.Load(bytes)`，此后**游戏运行中也能覆盖** `Mods\RimDelegation\Assemblies\RimDelegation.dll`（实测覆盖成功，原版下必然 ERROR 32）。⇒ `deploy.ps1` 里那段"检测到游戏在运行就 throw"的预检，在**启用 Doorstop 时**不再必要；未启用时仍然必要。

## 1. 当前部署结构：锁的是哪一个文件

你的流程（`build.ps1` / `deploy.ps1`）：

```
D:\Game\Rimworld Dev\RimDelegation\Assemblies\RimDelegation.dll        ← build.ps1 写
        ↓ robocopy /MIR（deploy.ps1）
C:\...\RimWorld\Mods\RimDelegation\Assemblies\RimDelegation.dll        ← 游戏实际加载
```

本机实测 `[验证]`：

| 位置 | 大小 | 修改时间 | 状态 |
|---|---|---|---|
| `Mods\RimDelegation\Assemblies\RimDelegation.dll`（游戏加载的） | 127,488 B | 2026/9/26 03:48 | 游戏运行期间被锁 |
| `D:\...\RimDelegation\Assemblies\RimDelegation.dll`（构建产物） | 160,256 B | 2026/9/26 17:17 | **独占读写打开成功 = 未被锁** |

- `Mods\RimDelegation` 是**真实目录**，不是符号链接（`LinkType` 为空）→ 游戏加载的是副本，不是工作区文件。
  - 所以**不要**改用 `deploy.ps1 -Link`：符号链接会让游戏直接加载工作区那份 dll，连 `build.ps1` 都会被锁，问题只会更严重。
- 结论：`build.ps1` 在游戏开着时也能成功；`deploy.ps1` 的 robocopy 写目标 dll 时必然拿到 Windows `ERROR 32`（文件被另一进程占用）→ robocopy 退出码 ≥ 8 → 脚本 `throw "robocopy 失败，退出码 N"`。这就是"提示 dll 占用，无法修改"。
- 附带发现：**你 17:17 构建的新版（160,256 B）还没进游戏**，游戏目录里仍是 03:48 的旧版。若你在游戏里看到的仍是旧行为，先确认部署这一步是否成功。

## 2. 原版为什么不重载 C#

> 本节讲的是**原版**行为（它的 hotReload 分支显式跳过程序集，且运行时没有可卸载程序集）。
> **第三方可以绕过**：§6 方案 4 的路子不是"卸载/换掉程序集"，而是**不卸载、只把目标方法的 IL 换掉**，
> 所以 §2.3 / §2.4 的结论（换程序集这条路走不通）依然成立，两者不矛盾。

### 2.1 加载方式锁文件

`Verse.ModAssemblyHandler.ReloadAll()` `[验证]`：

```csharp
public void ReloadAll()
{
    if (!globalResolverIsSet) { AppDomain.CurrentDomain.AssemblyResolve += ...; globalResolverIsSet = true; }
    foreach (FileInfo item in from f in ModContentPack.GetAllFilesForModPreserveOrder(mod, "Assemblies/", e => e.ToLower() == "dll")
                              select f.Item2)
    {
        assembly = Assembly.LoadFrom(item.FullName);   // ← 就地映射该文件，进程存活期间不能覆写/删除/改名
        if (AssemblyIsUsable(assembly)) { GenTypes.ClearCache(); loadedAssemblies.Add(assembly); }
    }
}
```

### 2.2 热重载分支**显式跳过**程序集

- 唯一调用点 `[验证]`（`find_callers` 只命中一处）：

```csharp
// Verse.ModContentPack
public void ReloadContent(bool hotReload = false)
{
    LongEventHandler.ExecuteWhenFinished(delegate { ReloadContentInt(hotReload); });
    if (!hotReload) { assemblies.ReloadAll(); }   // ← hotReload 时为 false 分支，程序集根本不重载
}
```

- 于是 `ModAssemblyHandler.ReloadAll()` 实际只在**启动时**跑一次。

### 2.3 就算你强行再调一次也没用

`Assembly.LoadFrom` 对**同标识程序集**返回已缓存的实例，不会再读磁盘字节 `[验证：LoadFrom 语义]` → 你拿到的还是旧代码对象。而且文件锁依旧存在。

### 2.4 运行时没有可卸载程序集的设施

RimWorld Windows 版跑在 Unity 的 **Mono / .NET Framework 4.7.2** 上，没有 .NET Core 那种可卸载的 `AssemblyLoadContext`（`AssemblyLoadContext` 类型本身在此运行时不存在）。"同一进程内换掉已加载代码"没有受支持手段。

## 3. 原版"Hot reload Defs"到底重载了什么

入口 `[验证]`：调试动作 `General → Hot reload Defs`（`Verse.DebugActionsMisc`，`[DebugAction(..., name = "Hot reload Defs", allowedGameStates = AllowedGameStates.Playing)]`）→ `PlayDataLoader.HotReloadDefs()`。

`PlayDataLoader.HotReloadDefs()` 做的与**不做**的事 `[验证]`：

- `LoadedModManager.LoadAllActiveMods(hotReload: true)`；hotReload 分支**跳过** `InitializeMods()`、`TKeySystem.Parse`、`ErrorCheckPatches()`。
- `ModContentPack.ReloadContent(hotReload: true)` → 如 §2.2，跳过 `assemblies.ReloadAll()`；且 `ReloadContentInt(hotReload: true)` **第一行就 `return`** → 贴图/音频/字符串/assetbundle **全都不重载**（贴图热重载是那个第三方 mod 补的，见 §4）。
- **没有** `DefOfHelper.RebindAllDefOfs()`、**没有** `StaticConstructorOnStartupUtility.CallAll()`、**没有** `TKeySystem.BuildMappings()`。
- 收尾会：重匹配地图上物体的 `ThingComp`（`Find.Maps` → `spawnedThings`）、`Pawn` 的 `hediff.Part` 重绑定、`Thing.Notify_DefsHotReloaded()`、`mapDrawer.RegenerateEverythingNow()`、关闭所有窗口。

Def 替换机制（关键）`[验证]`：

```csharp
// LoadedModManager.ParseAndProcessXML(..., hotReload: true)
if (hotReload) {
    Def defSilentFail = GenDefDatabase.GetDefSilentFail(def.GetType(), def.defName);  // 找旧的同名 Def
    if (defSilentFail != null) { toHotReloadCopy.Add((def, defSilentFail)); def = defSilentFail; }
}
// 稍后：Gen.MemberwiseShallowCopy(item, item2)   // 签名 MemberwiseShallowCopy(object from, object to)
//       即把【新解析的字段】灌进【旧实例】，并保留旧实例的 shortHash/index/debugRandomId/modContentPack/treeNode
//       新对象 item.defName += "_HotReloadedThrowaway" 后被丢弃
```

→ **对象身份保留**是它能安全热重载的原因：`DefOf`、存档里/对象上持有的 `Def` 引用继续指向同一个实例，只是字段被换成了新 XML 的值。

## 4. Hot Reload mod（workshop 3610957393 / `xiaoeyun.hotreload`）能力边界

已确认这个 mod **已启用**在你的 `ModsConfig.xml` 里 `[验证]`。

- **不支持程序集热重载**：整个程序集 21 个类型里搜索 `Assembly` 命中 0，字符串 `dll` 命中 0；配置类 `HotReloadConfig` 只有 5 个字段 `enabled / assets / defs / watch / api`。它引用的 `Microsoft.CodeAnalysis` 命名空间下只有一个编译器生成的 `Microsoft.CodeAnalysis.EmbeddedAttribute`（Roslyn 自动产物），**不是运行时编译**——不要被依赖名误导。
- 它实际做的事 `[验证]`（`HotReloadCore.ReloadMods`）：
  - `defs` → `PlayDataLoader.HotReloadDefs()`（即原版那套，继承 §3 的全部限制）
  - `assets` → 逐个 mod 的 `ModContentHolder<AudioClip>` / `<Texture2D>` / `<string>.ReloadAll(false)`
- 启用方式 `[验证]`（`HotReloadCore` 静态构造函数）：遍历 `LoadedModManager.RunningMods`，找 **`<mod 根目录>\hotReload.json`**，`enabled:true` 才登记；然后再按 `watch` / `api` 起监视和服务器。
  - HTTP：`GET http://localhost:8700/`、`POST http://localhost:8700/hot-reload`
  - 监视：`FileSystemWatcher(mod.RootDir)`，`IncludeSubdirectories = true`、`Filter = "*.*"`、500 ms 去抖 → **部署动作本身就会触发一次重载**
  - **这个 json 只在启动时扫一次**，新增/修改它必须重启游戏。
- **你现在实际在用它热重载的是美术包，不是 RimDelegation** `[验证]`（`Player.log`）：
  ```
  * RimWorld Hot Reload *
  Mods: WuwaHairStyle, WuwaEyePack
  Auto reload: Enabled
  [HotReload] Reload Defs / Reload AudioClips / Reload Textures / Reload String Assets   （出现两轮）
  ```
  配置分别在 `Mods\WuwaEyePack\hotReload.json`、`Mods\WuwaHairStyle\hotReload.json`、workshop `3604442772\hotReload.json`。
  → **RimDelegation 和 RimDelegation-RadiusUI 都没有 `hotReload.json`**（工作区与部署目录都没有），所以 Hot Reload mod 对 RimDelegation 目前"什么都没做"。
  → 这也解释了这个 mod 的真实价值定位：**给美术包热重载贴图**，不是给代码 mod 热重载 dll。

## 5. 对 RimDelegation 的四条具体限制（建议写进开发约定）

1. **改已有 Def 的数值/字段 → 可热重载**（对象身份保留，§3 机制）。矿区速率、超时天数、心情代价、战斗参数等调参走这条路，不用重启。
2. **新增 / 改 defName → 不行**：热重载路径不调 `DefOfHelper.RebindAllDefOfs()`，`[DefOf]` 静态字段会保持 null（原版只在启动和 `DoPlayLoad` 里重绑）。新增一种委派玩法必须重启。
3. **`[StaticConstructorOnStartup]` 不会重跑**：`StaticConstructorOnStartupUtility.CallAll()` 只在完整启动流程末尾调用。所以 ModBoot 的启动自检（`DelegationEventDef` / `DelegationFoodMoodDef` / SiteComps 三处）以及任何静态缓存**在热重载后都是陈旧的**——"静默失败要喊出来"这条准则是失效的，别把热重载后的自检输出当成有效验证。
4. **世界地图对象完全不在热重载清理范围内**（对 RimDelegation 最致命的一条）：`HotReloadDefs` 只遍历 `Find.Maps` 的 `spawnedThings` 和 `PawnsFinder`；`Notify_DefsHotReloaded` 只存在于 `Thing` / `ThingWithComps` / `ThingComp` / `Pawn`（外加 3 个建筑），**没有 `WorldObject` / `WorldObjectComp` 版本**。
   → 你的 `WorldObjectComp_Delegations` 挂在世界地图 Site 上：热重载后既不重匹配 comp、也收不到通知，进行中的委派会处于"半热"状态（Def 字段是新的，comp 实例与内部状态是旧的）。
   → **建议**：只在主菜单 / 新开局热重载；或在游戏内热重载前先结清/暂停所有在途委派。

## 6. 如果确实想减少重启（按性价比排序）

### 方案 1（推荐）：C# 走重启，XML 走热重载；顺手修掉部署被锁

要让"游戏开着改 XML 就能看到效果"真正好用，需要三处调整：

1. `hotReload.json` 放在**工作区**（`D:\Game\Rimworld Dev\RimDelegation\hotReload.json`），让 robocopy 把它带进部署目录。
   ⚠️ **不要**直接放在 `Mods\RimDelegation\`：`deploy.ps1` 用的是 robocopy `/MIR`（= `/E /PURGE`），**只存在于目标目录、源目录没有的文件会被删掉** `[验证：/MIR 语义 + 当前目录差异为空]`。
2. `deploy.ps1` 增加"仅同步非程序集内容"的模式（例如 `/XD <src>\Assemblies` 或新开关 `-SkipAssembly`）。否则游戏开着时 robocopy 因目标 dll 被锁而返回退出码 ≥8，脚本抛异常——即使 XML 已经复制成功，你也会以为部署失败。
3. 记住 §5 的四条限制，别拿热重载去验证新增 Def 或启动自检。

### 方案 2（真正解决"锁"）：两段式加载（launcher + payload）

原理：原版**只扫 `Assemblies/` 下的 `.dll`** 并 `LoadFrom`（只有这些会被锁）。把真代码放到 `Assemblies/` **之外**（如 `RimDelegation/Payload/RimDelegationPayload.dll`），由 `Assemblies/` 里一个极少改动的 launcher 读字节加载：

```csharp
var asm = Assembly.Load(File.ReadAllBytes(payloadPath));   // 读字节 → 不锁文件
content.assemblies.loadedAssemblies.Add(asm);              // ① 必须注册
GenTypes.ClearCache();                                     // ② 必须清缓存
```

三个必须做对的地方（都有反编译依据）：

- ① `GenTypes.AllActiveAssemblies` **只**遍历 `Assembly.GetExecutingAssembly()` + 各 mod 的 `mod.assemblies.loadedAssemblies`（该字段是 `public List<Assembly>`）。**不注册进去，XML 里的 `compClass` / `workerClass` 字符串就解析不到你的类型**（`GenTypes.GetTypeInAnyAssembly` 按这个顺序找，先命中先返回）。
- ② `GenTypes.AllTypes` 是懒加载缓存的，加载新程序集后要 `ClearCache()`。
- ③ **时机必须早于 Def XML 解析**：`LoadedModManager.LoadAllActiveMods` 的顺序是 `LoadModContent()`（装 dll）→ `CreateModClasses()` → `LoadModXML()`。而 `CreateModClasses()` 会实例化 `typeof(Mod).InstantiableDescendantsAndSelf()` 里的每个 `Mod` 子类，并按 `modpack.assemblies.loadedAssemblies.Contains(type.Assembly)` 反查宿主 mod。
  → 把 launcher 写成一个 **`Mod` 子类的构造函数**即可在 Def 解析前执行；`[StaticConstructorOnStartup]` **太晚**（`CallAll()` 在整个 `DoPlayLoad` 末尾）。

**代价 / 边界**：只解决"文件能不能写"（游戏开着也能构建、部署），**仍然必须重启游戏才生效**——旧程序集卸载不掉。多一层间接，payload 不在 `Assemblies/` 下也不受原版 `AssemblyIsUsable` 检查。

### 方案 3（不建议）：不重启就换 C#

只能靠"把 `loadedAssemblies` 里的旧条目换成新程序集 + 清缓存"制造新的类型身份，而旧类型实例（存档里的 `WorldObjectComp`、在途 `Delegation`、静态单例）**无法迁移**。RimDelegation 是 Def 驱动 + 状态住存档的结构，这条路会产出"同名两个类型、旧实例继续跑旧代码"的诡异行为，排查成本远超收益。

### 方案 4（2026-09-30 已实测跑通）：Doorstop + ILReloaderLib —— "方法级"代码热重载

**结论：C# 可以热重载，但只换"方法体"，且靶子方法有硬性筛选条件。** 本机环境：RimWorld 1.6.4871 rev591 / Unity 2022.3.35f1 / Harmony 2.4.1。

**工具与安装**
- [pardeike/Rimworld-Doorstop](https://github.com/pardeike/Rimworld-Doorstop) v1.8.2.0（`Doorstop.dll`，2026-03-04 发布）
- [Unity Doorstop](https://github.com/NeighTools/UnityDoorstop) v4.4.0（`winhttp.dll`；上游 README 明示测试过这个组合）
- [pardeike/ILReloader](https://github.com/pardeike/ILReloader) 的 ILReloaderLib v1.0.5（已内嵌进 Doorstop.dll）
- 游戏根目录放 `winhttp.dll` / `Doorstop.dll` / `doorstop_config.ini` / `.doorstop_version`；ini 里 `[Harmony] harmony_library=` 指向 `0Harmony.dll`（本机 = `workshop\content\294100\2009463077\Current\Assemblies\0Harmony.dll`）。**卸载 = 删这四个文件。**

**机制**（读 ILReloaderLib 源码）`[验证]`
- `AssemblyLoadingPatcher` 把 `ModAssemblyHandler.ReloadAll` 里的 `Assembly.LoadFrom` 换成 `Assembly.Load(bytes)`（顺带解掉 §1 的文件锁），并登记**所有** `[Reloadable]` 成员（Id = `声明类型全名.方法名(参数类型全名)`）。
- `Reloader` 用 `FileSystemWatcher("Mods", "*.dll", 递归)` 监视；文件一变，用 Mono.Cecil 读新 dll、用 Harmony transpiler（`priority=int.MaxValue`）把**新方法体的 IL 整体**灌进旧方法 ⇒ 类型身份与实例字段都不变。

**实测证据链** `[验证]`（游戏根目录 `output_log.txt`）

| 环节 | 证据 |
|---|---|
| 启动期登记 | `[Info] registered: RimDelegation.RimDelegationMod.HotReloadProbeText` |
| 运行中覆盖 dll | 覆盖成功（原版 `LoadFrom` 会 ERROR 32） |
| 触发重载 | `[Info] reloading …\Mods\RimDelegation\Assemblies\RimDelegation.dll` |
| 替换方法体 | `[Info] patching static System.String …HotReloadProbeText() with …` |
| 肉眼可见 | 设置窗口里的探针文字**不重启、不重开窗口**当场从 v1 变 v2（用户确认） |
| 游戏健康 | RimWorld 自身异常 0 条 |

**三条边界** `[验证]`
1. **构造泛型会让替换失败**：靶子方法体里只要有构造泛型操作数、或调用了带泛型实参参数的方法（`Nullable<T>` / `List<T>` / `Dictionary<K,V>` …），替换就抛 `TypeLoadException: Could not resolve type System.Nullable`1<Verse.TipSignal>`。根因：`Tools.ResolveType` 用 Cecil 风格名 `asm.GetType("X`1<Y>")` 查询，而 .NET 的类型名解析器只认 `[[…]]` 形式。⇒ `DoSettingsWindowContents` 这类 UI 方法天生中招，**靶子必须是"只碰非泛型类型"的小方法**。
2. **重复替换抛 NRE**：同一个文件被连续两次事件触发时，第二次在 `CecilConverter.Register` 抛 `NullReferenceException`；它发生在 `Unpatch` 之前，所以**第一次的替换依然生效**（无害，但别让一次改动触发两次）。
3. **可热重载的方法集合在启动时登记** ⇒ 新增/取消 `[Reloadable]` 都必须重启一次游戏才生效。

**可用打法**
1. 把要热改的逻辑隔离成小方法：`[Reloadable]` + `[MethodImpl(MethodImplOptions.NoInlining)]`（后者防止 JIT 把小方法内联进调用点），只碰非泛型类型；由**不标注**的普通方法调用它。
2. 循环：改代码 → 重编译 → 覆盖 `Mods\RimDelegation\Assemblies\RimDelegation.dll`（游戏开着也行）→ 1–2 秒生效。
3. 判定成功看三行日志：`registered:` → `reloading` → `patching`（**后面没有 `[Error]`**）；有 `[Error]` 就是踩了上面的边界。

**代价与风险** `[验证]`
- **会让 `ModRequestAPI`（workshop 2944488802）失效**：装 Doorstop 前那局零报错，装后 `TypeLoadException: Could not resolve type … ModRequestAPI.Models.MissingModRequest` 被跳过（A/B 证据）。原因是启动期要枚举**每个** mod 程序集的全部类型/方法并读特性。
- **满列表启动有"清空 mod 列表"的风险**：2026-09-30 那次 Doorstop 启动触发了 RimWorld 的 `PlayDataLoader` 自保（`ModsConfig.Reset()`，`Prefs.resetModsConfigOnCrash=true`），`ModsConfig.xml` 被写成只剩 Core+5 DLC（事后已用 9/27 存档的 `<modIds>` 还原 149 项）。
- **建议**：要热重载时用**最小列表**（`brrainz.harmony` + Core + 5 DLC + 目标 mod），用完把 `enabled=false` 关掉；日常游玩保持关闭。
- 需要改**游戏本体目录**（`winhttp.dll` 注入），Steam 校验/重装会清掉，需重装。
- `Assembly.Load(bytes)` 装载的程序集 `Location` 为空串；同一个 0Harmony 会被多个 mod 各加载一份（实测日志里有 6+ 条 `[Info] loading …0Harmony.dll`）。

**历史方案对照**

| 方案 | 结论 |
|---|---|
| [pardeike/Reloader](https://github.com/pardeike/Reloader)（2016–2018） | Detours + `[ReloadMethod]`，要求每次递增 dll 版本号；**已停更**，被本方案取代 |
| [Zetrith/Prepatcher](https://github.com/Zetrith/Prepatcher)（活跃） | 启动期用 Cecil 重写整个程序集栈 + 就地重跑加载流程；能"换程序集"，但代价是重跑一遍启动，**无助于缩短开发循环** |
| §2 方案 3（换掉 `loadedAssemblies` 里的旧条目） | 不必自研了：本方案的"只换方法体"路线正好回避了类型身份迁移问题 |
