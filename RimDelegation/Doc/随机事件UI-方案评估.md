## 2. 你的四类分级 → 落地建议

给 `DelegationEventDef` 加一个 4 级字段（比复用 `letterDef` 更准确 —— 信件的颜色语义和"这件事有多严重"不是一回事）：

```csharp
public enum DelegationEventSeverity { Flavor, Minor, Major, Boon }
public DelegationEventSeverity severity = DelegationEventSeverity.Minor;
```

现有 5 条事件的分级建议：

| 事件 | 建议分级 | 理由 |
|---|---|---|
| 闹别扭（Mood） | **Flavor** 或 Minor | 只有心情影响，没有进度代价 |
| 作业受挫（Setback，停摆 3–8h） | Minor | 纯时间损失 |
| 塌方（CaveIn，损失矿石 + 停摆 1–4h） | **Major** | 有实际资源损失 |
| 工伤（PawnAccident，真的见血） | **Major** | 唯一改 pawn 健康的事件 |
| 富矿脉（RichVein，+规模） | **Boon** | 收益 |

**弹信策略**（直接解决你说的"过度弹窗打断心流"）：

| 分级 | 信件 | Message | 流程块内联 | 日志 |
|---|---|---|---|---|
| Flavor | ✗ | ✗（可选 ✔） | ✔（淡灰一行） | ✔ |
| Minor | ✗ | ✔（`MessageTypeDefOf.CautionInput` 之类） | ✔ | ✔ |
| Major | ✔（保持现状） | ✔ | ✔ | ✔ |
| Boon | ✔ | ✔ | ✔ | ✔ |

红线：**Major 不许降级成静默** —— 项目已有"静默失败必须喊出来"的准则，见血/损失资源的事必须有信。

## 3. 显示方案（列全 + 推荐）

### 方案 A（你的原案）内联插入式：当前阶段下方"长"出一个子节点

```
● Denia 正在带领远行队移动…（0.6h / 2h）
    Chisa 打头，队伍绕开了一片看起来不太欢迎人的沼泽。
    [=====───────────────]              预计还需 1.4h
  ! 工具损坏加上恶劣天气，作业停摆 5.2 小时。      ← 内联事件行（黄）
    [=====╱╱╱╱╱╱╱╱╱╱╱╱╱╱]  停摆中 · 剩余 5.2h    ← 冻结的条
```

优点：和 S14 阶段模型天然契合（**就是多一类行**）；缺点：`Rows` 要新增行类型，且"事件行何时消失"要定规则。

### 方案 B 事件区块：流程块下方独立一小段"最近事件"

```
流程：
· 侦察环境（Chisa · 耗时 1h）
● 全队 搬运中（8.4/40 件） …
最近事件：
  ! 作业受挫（停摆 5.2h）— 工具损坏加上恶劣天气…
  · 队伍闹别扭 — 3 个人心情受影响。
```
优点：天然可折叠、可留存、不挤当前阶段；缺点：与"当前正在发生什么"距离远一点。

### 方案 C 只进日志：流程块不动，事件全进"远行日志"

优点：心流最不被打断；缺点：玩家可能整局没注意到"为什么进度停了"（**停摆必须在流程块里可见**，否则就是前面说的"静默"）。

### 推荐：**A 的变体 + B 的留存**

1. **把停摆做成流程块里的一个真阶段行**（而不是额外的"子节点"概念）：
   `● 停摆中（还剩 5.2h）` + 黄条冻结 + 一行事件描述 —— 复用现有 `Rows`/`StageRowsHeight`，**零新 UI 概念**。
2. **事件日志**做在**主控台右栏一张卡**（或页签尾部），点击展开完整列表（谁受伤、损失多少、谁在处理都在 `detail` 里）。日志**持久化**、委派结束后仍可查（你要的"Expedition Log"）。
3. **Flavor/Minor 不弹信**，只在流程块与日志里出现 —— 这一条对心流的改善最大，且实现成本几乎为零。

## 8. 简化方案（S15-b · 你提的"不发信、只做流程内叙事、不做 Major Crises"）

### 8.1 先拆一个概念：不发信 ≠ 没有机制影响

现有 5 条事件**全部是机制事件**（不是纯叙事）：

| 事件 | 机制影响 |
|---|---|
| 塌方 | 扣掉已采矿石 **+ 停摆 1–4h** |
| 作业受挫 | **停摆 3–8h**（照计计划天数） |
| 工伤 | 真的 `TakeDamage`（改 pawn 健康） |
| 闹别扭 | 给全队挂心情记忆 |
| 富矿脉 | 改事件点总规模（要挖更久） |

所以"只做叙事趣味"这句话：对**以后新增**的事件成立；对这 5 条**不成立** —— 它们是玩法机制。可以摘掉它们的**信件**，但不能摘掉"玩家得知道发生了什么"。

### 8.2 原版信件到底会不会打断游戏？`[验证]`

1.6 里 `LetterDef` 的字段是 **`pauseMode`**（旧版的 `pauseIfUrgent` 已经不存在）。实测四个原版 LetterDef：

| LetterDef | pauseMode |
|---|---|
| `NeutralEvent` / `PositiveEvent` / `NegativeEvent` | `AnyLetter` |
| `ThreatSmall` | `AnyThreat` |
| `ThreatBig` | `MajorThreat` |

而玩家的自动暂停设置（`Prefs.automaticPauseMode`）**默认是 `AnyThreat`** ⇒ **这些随机事件信默认不会暂停游戏**。
只有当玩家自己把设置调成"任何信件都暂停"（`AnyLetter`）时，事件信才会真的暂停。

⇒ 真正的"打断"其实是三件事：**信件区堆积** + **左上角图标** + （`AnyLetter` 设置下的）暂停。

### 8.3 简化后的形态（推荐照此落地）

| 档 | 内容 | 提示方式 |
|---|---|---|
| **Flavor** | 纯叙事，零机制（新增的那批） | **什么都不弹**：流程块内联一行 + 日志一条 |
| **Effect** | 有机制（停摆 / 损失 / 伤害 / 心情） | **不发 Letter**，改 `Messages.Message(text, …, historical: true)`：屏幕顶部一条短提示、几秒后消失、可回"消息记录" |

- 分级从 4 档砍到 **2 档**，"Major Crises"这类**不新增**；
- 现有 5 条按影响大小配色：**黄** = 时间损失（受挫/塌方），**红** = 见血 / 损失资源（工伤），**青** = 收益（富矿脉），**灰** = 只有心情（闹别扭）；
- **停摆仍然必须出现在流程块里**（§3 的"事件即阶段"）—— 进度停了却不写原因，那就是静默。

### 8.4 一条红线，需要你点头

**工伤 / 塌方这类"已经造成事实影响"的事件，即使不发信，也必须至少留下 `Message` + 流程块行 + 日志三者之一**（我建议三者都给）。
否则玩家两小时后发现"少了 7 单位矿石""有人带伤"却查不到任何记录 —— 这违反项目既有的"静默失败必须喊出来"准则。

### 8.5 顺带的好处

叙事事件（Flavor）的成本极低：**一个 Def + 一句话**，不用平衡数值、不用考虑与 worker 的交互。可以快速堆到 20–30 条 —— 这是"让世界不是静止的"最便宜的杠杆。
前提是**有可见落点**（流程块一行 + 日志一条）：玩家看不到的叙事等于白写。

## 9. 结论

**你的方向对，但要分两类走**：

1. 新增的**纯叙事事件**（Flavor）：不发信、不进信件区，只进流程块与日志 —— 完全照你说的做；
2. 现有的**机制事件**：摘掉 Letter 可以，但换成 `Message`（不打断、可回查）并在流程块里可见；
3. **不做 Major Crises** 没问题（分级只留 Flavor / Effect 两档）；
4. 无论哪类，**停摆与事实损失都必须可见**（流程块行 + 日志）。

需要你确认两件：① 机制事件换成 `Message`（而非完全静默）可以吗？② 日志就放主控台右栏卡，对吗？

## 11. S15-c：结束报告 / 左栏历史 / 完成时签核（你这一轮的三个设想）

### 11.1 "事故只写进完成或中断的日志" —— 可以，而且**已经有一半**

现在的 `Complete` / `Abort` 信件与检视摘要里**已经**写着：

- `期间发生 N 次随机事件（最近：XX）`
- `停摆 X 小时`
- 累计作业 / 休息 / 暂停小时数、结束理由、产出汇总

缺的只是**逐条明细**（哪一件、损失多少、谁受伤）—— 因为事件文本目前不存档（§1 缺陷①）。
所以"写进完成/中断日志"这条路，实质工作量 = **补那份存档** + 把明细追加到信件正文。

⚠️ 但**不能只写在那里**：委派可能还要跑好几天，而工伤已经扣了血、塌方已经埋了矿。
建议分工：

| 时机 | 呈现 |
|---|---|
| 进行中 | **流程块里一行**（零弹窗：不发 Letter、不发 Message）；停摆期间显示"事件即阶段"的 stall 行 |
| 结束时 | 明细汇总进完成/中断信件 +（可选）报告窗口 + 历史记录 |

### 11.2 左栏"历史记录" —— 三件里**最贵**的一件

现状：`DelegationRegistry` 只有 `AllActive()` / `AllPlanned()`；完成或中断后 `active = null`，而**采空会 `site.Destroy()`** ⇒ 现在没有任何可查的历史。

| 做法 | 代价 | 评价 |
|---|---|---|
| **A. 新建世界级 `GameComponent`**（存档级）持有 `List<DelegationRecord>` | 新增一个组件 + Scribe + FIFO 上限 | **推荐**：地点销毁了记录还在，跨地点可查 |
| B. 挂在地点的 `WorldObjectComp_Delegations` 上 | 几乎零新增 | 省，但**地点一销毁记录就没了**（采矿采空正好会销毁） |
| C. 只存 `ModSettings` 里最近 N 条 | 最省 | ❌ 不进存档（换档会串、读档会丢），不符合"历史"语义 |

记录字段建议：`defName` / 地点名 / 起止时间 / 结束理由（收工或中断+原因）/ 产出 / 作业·停摆时长 / 事件明细。上限 50–100 条 FIFO。
UI：左栏加一个可折叠的**「历史」**分组（复用现有状态分组与 `QuickSearchWidget`），选中后右栏显示完整报告。

### 11.3 "完成时签核"勾选项

- **位置**：两端底栏「固定」左边（原版底栏也要加；皮肤底栏现在是 `固定 | 暂停 | 加班 | [结束加班] | 中止`，宽度要算）。
- **弹框不暂停**：`[反编译]` `Verse.Window.forcePause` 字段存在，设 `false` 即可。
  ⚠️ 但**光设它不够**：还要 `absorbInputAroundWindow = false` + `closeOnClickedOutside = true` —— 否则窗口会**吃掉鼠标**（玩家在世界地图上点不了东西），那比暂停还烦。
  可参考的现成件：项目自己的 `Window_Delegations`（GameUI + draggable + resizeable）与 `Dialog_*` 系列。
- **勾选项存哪**：
  - **全局偏好**（`RimDelegationSettings`，Mod 设置、不进存档）—— 推荐，语义就是"以后委派结束给我报告"；
  - **每条委派**（`Delegation.reportOnComplete`，跟存档走）—— 更精确但要两端 UI 都带状态。
- **报告内容**：直接复用 11.1 的同一份明细，**不要写第二份文案**（项目准则：同一句话只允许一处实现）。

### 11.4 分期建议

### 11.6 打断版的三个实现注意

1. **暂停期间世界时间不走** ⇒ `TickDelegation` 自然停摆：报告窗口开着时委派不会推进（符合预期，不需要额外代码）。
2. **多条委派可能同时完成**（同一 tick 前后各一条）：用 `onlyOneOfTypeAllowed = true` + **排队**（关掉一个再弹下一个），否则两个报告窗口会叠在一起。
3. **报告文本只有一份来源**：窗口与信件必须复用 11.1 的同一份明细，不许写第二份格式化（项目准则：同一句话只允许一处实现）。

## 13. 第一期 · 实装记录（S15，已 build + deploy）

### 第一期 · 信息架构（事件可见 → 可查 → 结束汇总）

**目标**：把"事件发生 → 玩家看得见 → 结束时汇总"整条链打通。**不新增任何 UI 面**，全部落在已有的流程块 / 信件 / 底栏上。

| # | 内容 | 要点 |
|---|---|---|
| 1 | **事件文本存档** | 新增 `DelegationEventLogEntry`（`defName` / `firedTick` / `severity` / `detail`）+ `Delegation.eventLog`（`Scribe_Collections.Look(..., LookMode.Deep)`）+ FIFO 上限（约 50 条）。**这是整条链的地基**——现在 `Apply()` 的文字只进信件、`recentEventDefs` 只作冷却 |
| 2 | **事件分级（两档）** | `DelegationEventDef.severity`：`Flavor` / `Effect`（不做 Major Crises） |
| 3 | **零弹出** | `FireEvent` **不再发 Letter**：`Flavor` 什么都不做，`Effect` 只写日志。红线靠第 4/5/8 项兜住 |
| 4 | **流程块内联事件行** | 当前阶段下方一行淡色事件摘要 + tooltip 给完整 `detail`（复用 S14 的行模型） |
| 5 | **停摆行（事件即阶段）** | 停摆期间在阶段序列插 `stall` 行：黄条冻结 + `停摆中 · 剩余 Xh` + 事件描述 |
| 6 | **结束报告** | 明细汇总进完成/中断信件（现在只有 `期间发生 N 次随机事件（最近：X）` + `停摆 X 小时`） |
| 7 | **报告窗口 + 全局勾选项** | `RimDelegationSettings.reportOnComplete`（Mod 设置）+ 两端底栏「固定」左边 checkbox；窗口 `forcePause = true` / `closeOnClickedOutside = false` / `doCloseButton = true` / `onlyOneOfTypeAllowed = true` + 多条完成时**排队** |
| 8 | **底部按钮角标（补强）** | 有"未查看事件"时，底部「委派」主按钮出一个小角标（变色/圆点），打开主控台即清零。`eventLog` 每条加 `seen` 标记（或存 `lastSeenEventTick`），存档在委派上 |

**验收点**：

- 采矿触发塌方：**没有任何弹窗、没有信件**；流程块出现事件行 + 黄色停摆行、进度条冻结；底部按钮出现角标；
- 打开主控台 → 角标清零；
- 完成时的信件里出现**逐条事件明细**（不再是只有计数）；
- 勾选"完成时报告"→ 完成时弹出**暂停**的窗口，点确认才关；两条委派同时完成 → 窗口排队不叠；
- 不勾选 → 只有信件，不弹窗。

**风险 / 注意**：新增 `Scribe` 字段对老存档安全（缺省即空列表）；去掉 Letter 后要确认"重大影响不会漏"——由分级 + 第 4/5/8 项共同保证。

| # | 内容 | 要点 |

| 3 | **右栏报告视图** | 选中历史条目 → 右栏显示完整报告（与第一期同一份数据结构，不写第二份格式化） |
